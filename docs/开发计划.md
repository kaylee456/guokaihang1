## 二、总体路线

一套「智能客户分析 Agent」，两层结构：

```
上层：3 个问题工作流（编排）   Q1 单客户诊断 · Q2 名单+融资 · Q3 关联图谱
下层：10 个原子能力（取数）    C1..C10，统一 Provider 接口
数据：本期 MockProvider（照真实表字段名造假数据）
      未来 DBProvider（接库），一键切换，业务层零改动
```

三个客户问题不是三套系统，而是同一批底层能力的三种组合。Q1 的能力包是可复用内核：Q2 = 名单过滤 + 批量跑 Q1-lite；Q3 = 关系扩散 + 逐节点跑 Q1 子集。

---

## 三、四个分析维度（能力基线）

1. **客户基本情况**：工商、主营、股东股权；财务（资产负债率/现金流/收入/利润）；我行业务（贷款/基金/存款/中间业务余额、信用评级、项目资产质量）
2. **经营财务状况**：经营分析（主营、重大项目投资、公司治理）；财务指标（偿债/盈利/运营能力）
3. **风险状况**：风险大数据平台预警、评级器重大风险事件、观察名单、征信提示
4. **客户管理情况**：准入、分类分级、客我供求关系、经营主责人、客户名单

## 七、关键技术要点

- **LLM**：Qwen3.6 是推理模型，`max_tokens` 要给足（思考吃 token，否则正文被截断为空），分析类调用 ≥ 2048；需要关思考传 `chat_template_kwargs:{"enable_thinking":false}`；抽取用低温(0.1-0.3)，综合建议略高(0.4-0.6)；analyze 超时建议 120s，含 2 次重试；前端进度用 SSE 流式。
- **Provider 抽象**：`PROVIDER_MODE=mock|db` 由 `.env` 控制，registry 统一分发。`MockProvider` 读 `mockdata/*.yaml`；`DBProvider` 留 TODO 契约，未来接库。
- **mock 即 schema 契约**：假数据照真实表名/字段名造，DTO/SQL/报告面向真实字段编程，接库零改动。
- **取数走固定 SQL**：C1-C10 是已知固定查询，用参数化 SQL/视图，不用 NL→SQL（`vanna` 留给未来"模板外临时提问"兜底）。
- **报告**：Markdown 主体（可转 PDF/Word）+ 结构化 JSON 供前端渲染。
