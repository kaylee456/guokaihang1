## 2026-09-22　客户业务信息查询 Skill 开发

### 一、今日目标

在既有财务问答 Skill 之外，新增「客户业务信息查询 Skill」：输入客户名称 CST_NM / 客户编号 CST_ID，检索 6 张客户业务统计表，返回 CST_ID、ORG_ID 及业务明细，标注数据来源表，禁止编造。

### 二、数据地基核实（连真实达梦库探查）

- **6 张 RPT 业务表均存在、各 100 行 / 100 个去重客户**，共用主键 `WORK_DT, ORG_ID, CST_ID, CST_NM`：
  - `RPT_CUST_CAPITAL_DETAIL` 客户资金信息统计表（仅公共键，无额外明细列）
  - `RPT_CUST_LOAN_DETAIL` 客户贷款信息统计表
  - `RPT_CUST_DEPOSIT_DETAIL` 客户存款信息统计表
  - `RPT_CUST_FUND_DETAIL` 客户基金信息统计表
  - `RPT_CUST_GUARANTY_DETAIL` 客户担保信息统计表
  - `RPT_CUST_MIDBUSINESS_DETAIL` 客户中间业务信息统计表
- **金额字段 `*_W`（原币）/ `*_WRMB`（折人民币）已是万元量级**，无需像财务 Skill 那样按 `display_divisor` 二次换算，原样返回。
- **参与人路径 `TBCCPNM0` 为空且无 CST_ID**（只有 `CST_FULLNM → ORG_ID`），无法据此拿到业务明细 → 实际检索走 `CST_NM → 6 表` 路径，该表仅保留占位说明。
- schema 文件（`data_dictionary.json` / `summary.txt`）只记录了 `RPT_CUST_LOAN_DETAIL` 一张表，且字段与实库有出入（文档 `CUST_NAME`/`LOAN_BAL_W` vs 实库 `CST_NM` + 合同类列）；本次以实库为准编码，schema 待回补。

### 四、API 端点

| 端点 | 输入 | 用途 |
|---|---|---|
| `POST /skill/customer_business/query` | `{"query": "自然语言"}` | 主入口，LLM 抽参 + 取数 + 合成 answer |
| `POST /skill/customer_business/fetch` | `{name_or_id, org_id?, tables?}` | 免 LLM 直取（前端 / 联调） |
| `GET /skill/customer_business/resolve` | `?customer=&org_id=` | 只解析客户，不取明细 |

#### 主入口返回结构

```json
{
  "status": "ok",
  "resolved": { "cst_id": "...", "org_id": "...", "cst_nm": "..." },
  "matched_tables": ["RPT_CUST_LOAN_DETAIL", "RPT_CUST_DEPOSIT_DETAIL"],
  "data": [ { "table", "label", "columns", "rows" }, ... ],
  "extracted": { "name_or_id", "org_id", "tables" },
  "answer": "**客户身份**\n- 客户名称：..."
}
```

`status` 取值：`ok` / `not_found` / `multiple` / `no_business_data` / `empty_input` / `error`。`answer` 字段恒存在：命中时基于 `data` 由 LLM 合成，其它状态用 `message` 兜底，绝不编造。

### 五、执行规则落地

1. 输入 CST_NM / CST_ID，在 6 表匹配，返回 CST_ID、ORG_ID + 业务明细。
2. 多表独立查询，`tables` 参数可指定子集，缺省查全部 6 张。
3. 名称多命中时列出全部候选（上限 50），**不自行过滤**，由上层用 CST_ID / ORG_ID 澄清。
4. 无匹配数据时明确返回「未查询到对应客户业务数据」。
5. 输出标注数据来源表名（每组含 `table` / `label`）。
6. 取数不经 LLM（确定性固定 SQL），仅抽参与合成走 LLM，杜绝编造。

### 六、验证结果

- **真实库 + 真实 DeepSeek 端到端全过**：按名 / 按编号唯一命中 → 6 表明细；「贷款和存款」→ 精确抽 2 表；「全部业务」→ 查全 6 表；「中间业务」→ 精确映射到中间业务表；不存在客户 → `not_found` + 标准文案不编造；`answer` 输出标注来源表、客户身份、金额带万元。
- **免库单测** `M0 smoke: all passed`（服务器未装 pytest，用文件内 `__main__` 跑）。
- **运行前置**：`env` conda 环境（Python 3.14.7）+ `set PATH=D:\dmdbms\bin;%PATH%` 才能加载 dmPython 的 `dmdpi.dll`。

### 七、权限控制方案（已设计，待落地）

流程：**前端传身份 → 前置解析可见机构 → 求 cst_id 白名单 → SQL 硬过滤（主闸）→ LLM 后置核实（补）**。

- 角色 → 范围：客户经理（本人管户，`C_CUST_TEAM_MEMBER.CDB_EMPID`）/ 分行用户（本机构 + 下辖，`CCBINS_REL` 递归 → `C_CUST_MGR_ORG.MGRMNT_ORG`）/ 总行（全放行）。
- 代码落点：新增 `backend/auth/`（`Principal` + `scope_provider` 抽象 + `mock_scope` / `db_scope`），与取数层解耦；`ask()` 增加可选 `principal` 参数，缺省=放行，**向后兼容**。
- LLM 核实是纵深防御最后一道，**不作主闸**——权限边界由 `WHERE cst_id IN (whitelist)` 强制。

**阻断点（P3 接真表前必须解决）：**
1. **编码不一致**：RPT 表 `ORG_ID` = `M26090001`（9 位，M 开头），组织授权表用 9 位 `CCBINS_ID` / `MGRMNT_ORG` / `BLNG_INSID`，二者对不上，缺映射规则 / 表。
2. **组织授权表全空**：`C_CUST_MGR_ORG` / `C_CUST_TEAM_MEMBER` / `CCBINS_REL` / `CCBINS_INF` / `EMPE` 均 count=0，无法真实验证，需先灌数。
3. P1（mock ACL + 强制过滤 + principal 接入）可先行，不阻塞现有功能。
